# 账户体系与数据隔离设计方案（#29 · 供技术评审）

> 关联文档：`design/business-architecture.md`（业务架构与功能清单 v3）
> 状态：**评审已通过，进入落地实施阶段**。
> 评审日期：2026-09-05；评审结论：通过；游客方案最终选型：方案 A（共享游客区）；封版版本：v20260907130（v130 起取消 #29-3 的强制首登改密，默认密码改为 `baofu123`；详见末节「全文修订记录」）。
> 目标：在现有 `milktea-trader` 单库（SQLite + SQLAlchemy）基础上，明确账户分层、各层数据边界与隔离强度，并补齐已知隔离缺口，确保"隐私不出本机 + 按账号隔离 + 支持多端共用同一部署"三原则不被破坏。

---

## 一、设计目标与约束

1. **隐私不出本机**：持仓、规则、信号、通知密钥等仅存本地库（SQLite），不上传未授权平台；仅对外拉行情 + 调用户自有 LLM/通知。
2. **按账号隔离**：不同 `user_id` 的业务数据（可投池、标签、规则、信号、画像、通知配置）互相不可见、不可串。
3. **多端共用同一部署**：部署一次（云端/局域网），PC 与手机通过同一链接访问，数据落在同一份库 → 天然跨设备；**不做**浏览器 `localStorage` 存储（用户明确拒绝）。
4. **游客可用但不污染**：游客可免登体验核心功能，但其写入须与正式账号隔离，且生命周期可控（可清理、不泄漏正式用户数据）。
5. **管理员可运维**：admin 可管理账号、查看全量（导出/备份），但**默认不混入普通用户业务视图**。

## 二、现状梳理（As-Is，基于 `backend/app/models.py`）

### 2.1 账户模型
- `User`：`role` ∈ {admin, user}；`is_guest` 布尔；`password_hash`+`salt` 加盐哈希；`must_change_pw` 字段已保留但**不再触发强制改密**（v130 起改用出厂默认密码 `baofu123` 兼顾首次登录体验）；`last_login_at/last_ip` 用于访问记录。

### 2.3 现有隔离结论
- **核心业务数据（可投池/标签/规则/信号/画像/通知/设置）已正确按 `user_id` 隔离** —— 这是本方案的基础，无需返工。
- **两处缺口需补齐**：`stock_tconfig`（应加 `user_id` 维度）、`access_logs`（游客应落 `user_id` 以便按账号追溯与清理）。

## 三、目标账户体系

### 3.1 三层账户
| 层级 | role / 标记 | 能力 | 数据范围 |
|---|---|---|---|
| **管理员 admin** | `role='admin'` | 账号管理、全量导出/备份、系统配置 | 可见全部用户数据（运维视图），但业务操作默认在自己账号上下文 |
| **正式用户 user** | `role='user'` | 全部个人功能 | 仅自己 `user_id` 下的数据 |
| **游客 guest** | `is_guest=True` | 免登体验可投池/看板/分析 | 独立隔离的游客工作区，不接触任何正式用户数据 |

### 3.2 权限矩阵（通用粒度）
> 按用户级约定，权限用「新增/修改/删除/导入/导出/查看」通用粒度，页面内具体操作归入"查看"子集，不单列。

| 能力 | admin | user | guest |
|---|---|---|---|
| 查看自己数据 | ✅ | ✅ | ✅(仅游客区) |
| 新增/修改/删除 个人业务数据 | ✅ | ✅ | ✅(仅游客区) |
| 导入/导出 自己数据 | ✅ | ✅ | ⚠️ 仅导出（不导入到正式区） |
| 管理账号（增删用户/重置密码） | ✅ | ❌ | ❌ |
| 全量导出/备份（所有用户） | ✅ | ❌ | ❌ |
| 查看他人数据 | ✅(运维) | ❌ | ❌ |

## 四、数据隔离边界（目标态）

### 4.1 隔离分区
```
┌─ 全局共享（非 PII，合理共享）───────────────┐
│ stocks · daily_quotes · scheme_types · app_settings │
└──────────────────────────────────────────────┘
┌─ 按 user_id 强隔离（PII / 个人业务）─────────┐
│ tracked_pool · pool_tags · position_rules ·       │
│ signals · screens · user_profile · notify_* ·    │
│ user_settings · stock_tconfig(补 user_id) ·      │
│ access_logs(补 user_id)                          │
└──────────────────────────────────────────────┘
┌─ 游客隔离区（独立 user_id，可整体清理）──────┐
│ 一个或多个 is_guest=True 的 User 记录，        │
│ 其业务数据完全落在游客 user_id 下              │
└──────────────────────────────────────────────┘
```

### 4.2 补齐缺口的改法
1. **`stock_tconfig` 加 `user_id`**：复合主键 `(user_id, code)`；存量数据按"首个正式用户"或"admin"回填 `user_id`，查询全部带 `user_id` 过滤。这样 A 用户给某股设的支撑/压力/风控备注，B 用户看不到。
2. **`access_logs` 加 `user_id`**（可空）：登录态记录 `user_id`；游客分配游客 `user_id` 后一并写入。清理游客时连其访问日志一同清理。

## 五、游客账户模型（评审结论：方案 A）

当前游客仅用 `is_guest` 标记，未明确"游客数据落在哪个 user 记录"。提出两种方案供评审：

- **方案 A（推荐 · 单共享游客区）**：固定一个 `guest` 系统账号（`is_guest=True`），所有游客共用其工作区。实现简单、体验连续；代价是游客之间数据不隔离（适合"演示/试用"定位，符合个人工具场景）。
- **方案 B（每会话独立游客）**：每次游客进入生成临时 `user_id`，会话/定期过期清理。隔离最干净，但实现复杂、游客体验不连续（刷新即丢）。

> **评审结论**：选定 **方案 A（单共享游客区）**。所有游客共用系统预设的 `guest` 账号工作区，确保"不污染正式用户数据"，同时降低实现复杂度与 token 消耗。若后续转为多人在线产品再升方案 B。

## 六、跨设备与隐私

- **同一份库 = 跨设备**：部署一次后，PC/手机通过同一链接访问同一 SQLite，天然多端同步，无需额外同步机制。
- **不使用 localStorage**：所有持久化走后端 SQLite；前端仅持 `token`（会话级，可过期）。
- **备份/迁移**：`/api/data/export-all`（admin，scope=all-users）整库导出；`/api/data/import-all` 整库恢复，支持换机/迁云。
- **隐私红线**：行情/持仓/规则/通知密钥不出本机；仅两类对外请求：①拉行情；②调用户自有 LLM/通知（密钥本地加密存储于 `user_settings`/`notify_config`）。

## 八、落地方案（评审已通过，进入实施）

**阶段 1 · 补隔离缺口（低风险）**
- `stock_tconfig` 增加 `user_id` 列 + 复合主键 `(user_id, code)`；存量按 admin 回填；所有读写加 `user_id` 过滤。
- `access_logs` 增加 `user_id`（可空）；登录态记录对应 `user_id`，游客分配 guest 账号后一并写入。

**阶段 2 · 游客模型定型与清理机制**
- 方案 A 落地：所有游客进入时统一映射到系统预设 `guest` 账号（`is_guest=True`）。
- 在**每天第一个游客登录/进入**时触发清理：删除 `guest` 账号下的 `tracked_pool`、`pool_tags`、`position_rules`、`signals`、`screens`、`screen_results`、`user_profile`、`notify_config`、`notify_log`、`user_settings`、`stock_tconfig`、`access_logs` 等游客工作区数据。

**阶段 3 · 账号管理闭环**
- admin 账号管理页（增删用户、重置密码、查询 `must_change_pw` 状态）。
- admin 默认密码 `baofu123` 登录即可使用，**不再强制跳转改密页**；如需提升安全性，admin 可在设置页自行修改密码（修改后 `password_hash` 即更新，下次登录用新密码）。

**阶段 4 · 文档与验证**
- 更新 `business-architecture.md` 账户章节；端到端验证：user A 不可见 user B 数据、游客不污染正式区、admin 用 `baofu123` 直接登录可用、跨设备同库同步。
